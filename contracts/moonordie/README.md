# Moon or Die in Sluice

This is an independent Sui package, not an upgrade to the existing vesting package. The Sluice interface can discover both. Its immutable commitment fixes a token quantity, beneficiary, market-cap target, deadline, minimum liquidity, data policy, and oracle quorum at creation.

## Exact settlement rule

- `PENDING -> SUCCESS`: one authenticated observation at or above the market-cap target is **recorded on-chain strictly before the deadline**. Observations must be no older than 120 seconds and cannot predate the deposit. No sustained window or gradual vesting applies.
- `SUCCESS -> CLAIMED`: anyone can sponsor a transaction that transfers the entire deposit to the fixed beneficiary. There is no claim deadline and no subsequent market-data dependency.
- `PENDING -> DISPOSED`: at or after the deadline, anyone can finalize permanent disposal. Neither successful nor claimed commitments can enter this path.

There is no cancellation, refund, beneficiary reassignment, oracle rotation, administrator withdrawal, or policy edit. The package must be published immutably using the supplied publication helper before accepting deposits.

**This is an observed-and-recorded target, not a guarantee about every historical price tick.** A market-cap spike that is missed by the oracle, fails liquidity checks, or is not recorded before the deadline does not qualify. Late attestations are rejected even if they carry a pre-deadline timestamp. This strict boundary removes the race where an expired deposit could be both released and disposed. There is no hidden evidence grace period. Feed/keeper outages can therefore result in disposal. The UI explains this before wallet signing.

The feed is DexScreener's highest-liquidity exact-base-token pair, using its `marketCap` field only. FDV is never substituted. Feed availability and liquidity are checked before creation and before observations. The canonical policy hash and domain-separated signatures bind evidence to one commitment. Oracle operators remain trusted to report honest data; running several keys on one machine does not create independent oracle security.

## What “disposal” means

The entire deposit is removed from the shared commitment and converted to a `Coin<T>` that is frozen with `transfer::public_freeze_object`. Sui immutable objects cannot be consumed or mutated. The frozen coin's ID is stored in the commitment and emitted in an event so users can inspect it independently. There is no recipient wallet or recoverable private key.

This permanently removes spendability, **not recorded total supply**. It is not advertised as a `coin::burn` supply reduction, which needs token-specific authority. Even a later version of another package cannot unfreeze an immutable coin. Pending deposits additionally rely on this package being immutable; the publication transaction consumes its UpgradeCap atomically.

## Build and verify

Use Sui CLI `1.73.2`; the framework dependency is pinned to that release's exact commit to avoid moving framework/VM incompatibilities. CI downloads the official release and verifies its SHA-256 before executing the Move tests.

```sh
sui move test --path contracts/moonordie
node --test tests/moonordie.test.cjs tests/sluice-relayer.test.cjs
npm run build:sluice
```

Move tests cover real Ed25519 signatures generated by the JavaScript encoder, immediate and post-deadline claims, irreversible freezing, replay/tampering, stale/future/pre-deposit samples, failed thresholds, and deadline boundaries. Node tests exercise keeper execution with simulated network/transaction boundaries. These are not claims of a completed testnet or mainnet deployment.

## Publication and activation

Publication costs Sui gas and is a separate operator action. No publication occurs when this PR is merged.

1. Build the package with `sui move build --path contracts/moonordie --dump-bytecode-as-base64` and save the JSON output as an artifact outside the public website directory.
2. Set `SUI_NETWORK=testnet` and `MOONORDIE_PUBLISHER_ADDRESS` to the funded test publisher's public address. Run `node scripts/moonordie-publish.js --build-json <artifact.json>` to simulate the immutable publication without signing.
3. After approval to publish, provide `MOONORDIE_PUBLISHER_PRIVATE_KEY` through a secure environment and run the same command with `--execute`. The helper publishes and calls `0x2::package::make_immutable` in **one transaction**. Inspect the transaction and record the actual package ID; never use a simulated package ID.
4. Use a separate oracle policy and gas sponsor for Moon or Die. Reuse `scripts/sluice-keygen.js` to generate keys privately. Do not put key output, environment files, or artifacts containing credentials anywhere under the Pages repository: its root is deployed publicly.
5. Run testnet canaries through both success/claim and failure/disposal paths. Because the normal feed selects Sui-mainnet market data, validate testnet token observations with an explicitly controlled test signer rather than pretending the test token has a mainnet market. Verify the frozen coin has immutable ownership and that the publication retained no UpgradeCap.
6. After approving mainnet deployment and the strict deadline policy, publish the reviewed immutable artifact to mainnet, run small canaries, and start the continuous keeper below.
7. Set public repository variables `MOONORDIE_PACKAGE_ADDRESS`, `MOONORDIE_ORACLE_PUBLIC_KEYS` (comma-separated raw 32-byte hex keys), `MOONORDIE_ORACLE_THRESHOLD`, and finally `MOONORDIE_READY=true`. Run the Pages deployment. Keep readiness false until immutable publication, canaries, and keeper monitoring are verified. The existing Sluice V2 settings are unchanged.

The web client supports wallet beneficiaries only in this mode. Private bearer links would require reassignment authority and are intentionally unavailable. Discovery, claims, and disposal remain available for an existing configured package even while new creation is disabled.

## Continuous keeper

Use Node 22+ on an existing always-on host; `ops/moonordie-keeper.service` is a systemd service template. Install the repository to `/opt/alphacity`, run `npm ci --omit=dev --ignore-scripts`, provision the service user, and store a restricted environment file at `/etc/moonordie/keeper.env` (outside the website checkout):

```text
SUI_NETWORK=mainnet
MOONORDIE_PACKAGE_ADDRESS=<immutable package ID>
MOONORDIE_ORACLE_PRIVATE_KEYS=<comma-separated private oracle keys>
MOONORDIE_RELAYER_PRIVATE_KEY=<dedicated gas sponsor private key>
MOONORDIE_POLL_MS=30000
```

Optional `SUI_GRAPHQL_URL` and `SUI_GRPC_URL` override public network endpoints. `MOONORDIE_DRY_RUN=true` performs reads without signing or submitting. `node scripts/moonordie-keeper.js` runs once; add `--watch` for continuous polling. Do not run multiple keepers with the same gas key, or share its gas key with the GitHub Sluice relayer.

The keeper submits only qualifying success observations (no gas spent recording below-target prices), batches market reads by token within a short cache window, waits for transaction finality, and rereads chain state each scan. It does not backdate timestamps to compensate for clock skew. Keep host time synchronized; future timestamps are rejected by the contract. Transactions are not blindly retried after uncertain outcomes. Stale indexer state can cause harmless transaction aborts; the contract enforces the current state.

Each scan emits a JSON heartbeat and failure counts. Errors include a low-gas warning below 0.05 SUI and scans exceeding the configured polling interval. Configure host monitoring to alert on these errors, service restarts, or no successful heartbeat for two minutes, and maintain gas funding. At larger scale, add observation capacity before scans exceed the sampling interval. The process and public feed cannot promise that every brief crossing is detected.

**Do not enable this irreversible mode using GitHub cron as the only keeper.** Its observed delays exceed the needed observation cadence. Reusing an existing host may avoid another hosting subscription, but gas and any new host/provider charges still need an operating budget. Exact deadline execution is not guaranteed; a delayed disposal transaction cannot make the deposit eligible for late success.
